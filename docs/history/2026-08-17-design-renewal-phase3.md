## #154 — 경계를 720px 이 아니라 520px 로 잡은 이유

처음에는 기존 720px 경계를 그대로 썼다. 그랬더니 **E2E 3건이 깨졌다** —
521~720px(태블릿 세로·좁은 창)에서 멀쩡히 쓰이던 위아래 분할과 세로 리사이저가
함께 사라졌기 때문이다.

못 쓰게 되는 것은 **휴대폰 폭**이므로 분할을 없애는 경계만 더 좁게 잡았다. 세
테스트(P9·E5·D6)는 375px 대신 **분할이 살아 있는 가장 좁은 구간(700px)** 에서
재도록 옮겼다 — 커버리지는 그대로다.

### 상태는 한 벌이다

이슈의 제약이 "두 벌의 상태를 만들지 말 것" 이었다. 저장 값은
`split|editor|preview` 그대로 두고 **표시만** `effectiveViewMode(mode, narrow)` 로
접는다. 직접적인 결과 두 가지:

- 좁은 화면에서 기본(`split`)은 `editor` 로 보이고 저장 값은 여전히 `split` 이다 →
  넓히면 분할로 돌아온다.
- 좁은 화면에서 사용자가 미리보기를 고르면 그 값이 저장되어 **넓은 화면에서도
  미리보기**다. 이것을 피하려면 좁은 화면 전용 값을 따로 둬야 한다.

## #155 — 자동 테스트의 한계를 먼저 인정했다

가상 키보드는 헤드리스 브라우저에 없다. 그래서 계산을 `virtualKeyboard.ts` 로
떼어 **자동으로 검증할 수 있는 부분만** 단위로 고정하고, 실기기 확인 절차는
이슈 댓글에 남겼다(#135 의 Finder 등록과 같은 성격).

**KB8 이 이번 회차의 수확이다.** `pointerdown` 의 `preventDefault()` 를 지워도
KB7(포커스 유지)은 통과했다 — 헤드리스에는 내려갈 키보드가 없기 때문이다. 그래서
결과가 아니라 **이벤트가 취소됐는지 자체**를 보도록 했다(트랩 #38 의 `dragover` 와
같은 방법).

서식 바는 `toolbarActionByLabel()` 로 찾은 **툴바와 같은 액션**을 실행한다. 서식
계산을 다시 구현하면 좁은 화면에서만 다른 결과가 난다.

## 승격 중에 발견한 것 두 가지

### 1. `npm run release` 가 이미 릴리스한 항목을 다시 실었다

기준 태그가 v2.4.0 으로 잡혀 v2.5.0 에서 이미 나간 5건이 CHANGELOG 에 또
들어갔다. 태그는 `main` 에 붙고 계산은 `dev` 에서 하므로 **승격 직후 로컬에는 늘
최신 태그가 없다.**

조용히 틀리는 종류라 `scripts/release.mjs` 에 가드를 넣었다 — **기준 태그가
`package.json` 버전보다 낮으면 중단**하고 `git fetch --tags` 를 안내한다. 단위 2건과
트랩 #101.

### 2. prod 검증에서만 실패한 테스트 (CP3)

앱은 정상이고 **단언이 불안정**했다. `selectionchange` 는 작업 큐로 들어가므로
입력 직후 한 번만 읽으면 도착 전일 수 있는데, 로컬에서 우연히 통과하고 있었다
(다시 돌리니 로컬에서도 실패했다).

여유를 넉넉히 주면 150ms 디바운스에 얹어도 통과해 지키려던 것이 사라진다(트랩 #68).
**디바운스보다 짧은 100ms** 안에 도착하는지를 재시도로 보게 고쳤고, 디바운스를
주입해 여전히 실패하는 것을 확인했다(PR #174, 트랩 #102).
