# 릴리스 노트 자동화 + 버전 관리 (이슈 #131)

## 요청

> 기능이 추가되고 배포될때마다 release note를 만들어주고, 버전을 올려줘.
> 최종 버전은 latest로 접근할 수 있게 해주고, release note 이력을 볼 수 있게 해줘.

## 시작 전에 물은 것

"latest 로 접근" 과 "이력 보기" 가 **어디**를 가리키는지에 따라 만드는 것이 완전히
달라진다 — 앱 안인지, GitHub Release 인지, 아니면 배포 자체를 버전별 URL 로 두는
것인지. 추측으로 만들면 다시 만들어야 하므로 물었다.

| 질문 | 사용자 결정 |
|------|-------------|
| 노출 위치 | **앱 안 + GitHub 둘 다** — 리포의 `CHANGELOG.md` 를 단일 출처로 |
| 버전 규칙 | **커밋 메시지 기반 자동** |

## 지금 상태였던 것

- `package.json` 은 `2.0.0` 인데 **태그 0개 · GitHub 릴리스 0개**
- 버전이 **앱 어디에도 표시되지 않았다**
- F-69 갱신 알림은 "새 버전이 있습니다" 만 말하고 **무엇이 바뀌었는지 안 알려줬다**

## 만든 것

### 단일 출처

```
CHANGELOG.md ─┬─ virtual:release-notes (빌드 시각) → 앱 "새 소식" 화면
              └─ scripts/changelog-section.mjs (CI) → GitHub Release 본문
```

두 곳에 따로 쓰면 반드시 한쪽이 낡는다. 한 파일에서 파생시킨 이유 전부다.

### 파일

| 파일 | 역할 |
|------|------|
| `CHANGELOG.md` | 단일 출처 (Keep a Changelog) |
| `src/releaseNotes.ts` | 파싱·버전 비교·자동 표시 판단 (순수) |
| `src/releaseNotesUi.ts` | "새 소식" `<dialog>` (주입형 리프) |
| `scripts/release.mjs` | 커밋 메시지 → 다음 버전 계산 + 두 파일 갱신 |
| `scripts/changelog-section.mjs` | 한 버전 절만 잘라 릴리스 본문으로 |
| `vite.config.ts` | `virtual:release-notes` 가상 모듈 |
| `.github/workflows/ci.yml` | `release` 잡 — 태그 + GitHub Release |

### 앱에서 보이는 것

상태 표시줄 오른쪽에 `v2.1.0`, 누르면 이력. **갱신 뒤 처음 열 때 한 번 자동으로**
뜬다 — F-69 알림이 "무엇이" 를 말하지 못하던 자리를 메운다.

**처음 온 사람에게는 띄우지 않는다.** 그 사람에게는 전부가 처음이라, 새 소식이
아니라 방해다.

### 버전 규칙

`feat:` → minor · `!`·`BREAKING CHANGE` → major · 그 밖 → patch ·
`docs`·`chore`·`test`·`style`·`ci`·`build` **만** 있으면 **올리지 않는다.**

마지막이 중요하다. 문서만 고친 배포까지 버전을 올리면 **빈 새 소식**이 뜨고,
그 경험이 반복되면 사용자가 알림 자체를 무시하게 된다.

## 지킨 제약 두 가지

### 1. 네트워크를 늘리지 않았다

이 앱은 공유(F-60) 외에 네트워크 요청이 **0건**이고 E2E `SH8` 이 그것을 단언한다.
`fetch("/releases.json")` 하나면 그 성질이 깨진다. 릴리스 노트는 배포 시각에 이미
확정된 값이라 받아올 이유도 없어서, **빌드 시각에 번들에 넣었다.**

커밋되는 생성 `.ts` 도 만들지 않았다 — 재생성을 잊으면 **빌드도 테스트도 통과하면서
화면만 옛 내용으로 남는다**(트랩 #22 의 아이콘 사고와 같은 구조). 가상 모듈은 매
빌드에 원본을 다시 읽으므로 낡을 수가 없다.

### 2. CI 가 커밋을 되밀지 않는다

`main`·`dev` 는 브랜치 보호라 push 가 거부된다. 그래서 버전 올리기는 **승격 PR
안에서** 끝나고, CI 는 머지된 결과를 **읽어서** 태그와 릴리스만 만든다.

**태그는 배포·헬스체크가 끝난 뒤에 만든다.** 태그는 "이 버전이 서비스되고 있다" 는
표식이어야 하고, 배포가 실패했는데 태그가 남으면 그 표식이 거짓말을 한다.

태그가 이미 있으면 조용히 끝낸다 — 문서만 고친 배포는 버전이 그대로라 이 경로로
오는데, 실패로 다루면 **정상 배포마다 빨간 X** 가 뜬다.

## 검증

### 의도적 버그 주입 6건 — 전부 잡힘

| 주입한 버그 | 잡은 테스트 |
|---|---|
| 사전순 버전 비교 (`2.10.0 < 2.9.0`) | 단위 3건 |
| 처음 온 사람에게도 새 소식 표시 | 단위 1건 |
| 여는 순간이 아니라 닫을 때 기록 | 단위 2 + E2E 1건 |
| 정화를 거치지 않고 본문 주입 | 단위 1 + E2E 1건 |
| `docs`·`chore` 도 버전 올림 | 단위 2건 |
| CHANGELOG 대신 빈 문자열 번들 | E2E 5건 |

### E2E 자기 함정 1건

`addInitScript` 는 **내비게이션마다 다시 실행된다.** "한 번만 뜬다" 를 검증하는데
그것으로 초기 상태를 심으면 새로고침에서 값이 되살아나 **영원히 첫 번째**가 된다.
`page.evaluate()` 로 바꿨다. (트랩 #76)

### 코드로 확인할 수 없어 실물로 확인한 것

머지 전까지 **태그가 0개**였고 `release` 잡은 main 전용이라 dev 에서 계속 skip 됐다.
즉 이 경로는 한 번도 실행된 적이 없었고, PR 본문에 그 사실과 확인 항목을 적어 두고
머지 후 실측했다:

| 확인 | 결과 |
|------|------|
| `deploy` → `release` 순서로 돌고 성공 | ✅ |
| 태그 생성 (브랜치 보호에 안 걸리는가) | ✅ `v2.1.0` — 태그 push 는 보호 대상이 아님이 실측됨 |
| 릴리스 본문 = `CHANGELOG.md` 2.1.0 절 | ✅ 일치 |
| `/releases/latest` → `v2.1.0` | ✅ |
| prod 앱의 버전 표시·새 소식 | ✅ |

릴리스 본문에서 **후행 빈 줄 1개** 차이가 있었다 — `gh release create` 가 본문 끝
공백을 정리한 것으로 내용은 동일하고 렌더 결과가 같아 고치지 않았다.

## 앞으로의 흐름

```
기능 커밋 → PR → dev 머지
  → npm run release   (승격 PR 안에서 버전·CHANGELOG 갱신)
  → main 머지 → 배포 → 헬스체크 → 태그 + Release 자동 생성
  → 사용자는 갱신 후 첫 실행에서 "새 소식" 을 한 번 본다
```

이번에는 태그가 없어 `2.1.0` 을 직접 지정했다. 태그가 생겼으므로 다음부터는
그 이후 커밋만 보고 자동 계산된다.

## 남은 것

- 릴리스 노트 문구는 커밋 제목에서 기계적으로 뽑히므로, **사람이 한 번 다듬는 단계**가
  여전히 필요하다 (`npm run release` 뒤 커밋 전)
- 앱의 "새 소식" 은 이력 전체를 담으므로 버전이 쌓이면 번들이 조금씩 커진다. 지금은
  2개라 무시할 수준이지만, 수십 개가 되면 최근 N개만 넣는 판단이 필요하다
