# E2E 골격 생성 스킵 — Q5 보호 (이슈 #8)

`aiops:dev-e2e` 는 이 저장소에 이미 성숙한 Playwright E2E 스위트가 있는 것을 확인하고
**템플릿 골격 복사(POM `pages/`, `full/`/`smoke/` 분리, `global-setup.ts` 등)를 하지
않았다.** 이 문서는 그 사유와, 이슈 #8(F-69 서비스 워커 업데이트 알림)의 E2E 를 이
프로젝트 컨벤션에 맞춰 어디에 어떻게 추가해야 하는지 정리한다.

## 왜 스킵했는가

- `playwright.config.ts` (루트)가 이미 존재하고 프로젝트에 맞게 구성돼 있다
  (`webServer` 로 vite dev 서버 자동 기동, `testDir: ./tests/e2e`).
- `tests/e2e/` 아래 7개 스펙(`urls`, `editor`, `toolbar`, `tabs`, `fileaccess`,
  `session`, `hardening`)과 `fixtures.ts`, `types.d.ts` 가 이미 정착된 컨벤션을
  갖고 있다.
- 이 프로젝트는 **백엔드·DB·어드민이 없는 100% 클라이언트 앱**이다
  (`.claude/config.json` `agent_hints.backend = null`). 표준 템플릿이 가정하는
  로그인/storageState/API 클라이언트/테넌트 픽스처 개념이 아예 존재하지 않는다.
  템플릿을 복사했다면 전부 걷어내야 했을 것이다.

## 이 프로젝트의 E2E 컨벤션 (요약)

| 항목 | 규칙 |
|------|------|
| 파일 배치 | flat `tests/e2e/<feature>.spec.ts` — `pages/`·`full/`·`smoke/` 서브디렉토리 없음 |
| 네이밍 | 기능 슬러그 소문자(`hardening`, `fileaccess`, `session`) — kebab/camel 혼재 없이 단일 소문자 단어 |
| 테스트 제목 | 한국어, `describe` 는 `"F-<번호> <기능명>"` 형식 (예: `"F-61 PWA"`) |
| 목 주입 | `page.addInitScript()` 로 앱 스크립트 실행 **전** 전역을 치환. 결과는
  `window.__xxxMock` 전역에 쌓고, `page.evaluate()` 로 조회하는 헬퍼 함수를
  `fixtures.ts` 에 export (`installFsMock`/`setFsMock`/`getWrites` 패턴) |
| 원격 전용 스킵 | `isRemote(baseURL)` 헬퍼(현재 `hardening.spec.ts` 로컬 정의) +
  `test.skip(!isRemote(baseURL), "사유 문구")`. 사유 문구는 사람이 읽고 바로 이해할
  수 있는 완전한 문장으로 쓴다 |
  | 타입 선언 | 목이 전역에 얹는 타입은 `tests/e2e/types.d.ts` 에 `interface Window` 보강으로 선언 |
| 인증 | 없음 — `global-setup.ts`/`storageState` 불필요. 모든 테스트는 깨끗한 컨텍스트에서 시작 |
| 격리/정리 | `localStorage` 세션 키(`markdown-editor:session:v1`)를 쓰는 테스트는 종료 시
  해당 키를 정리한다(명시적 afterEach 또는 새 컨텍스트 사용) |

## 이슈 #8 (F-69) E2E 를 어디에 추가할지 — 판단 및 근거

**기술 스펙(§13.1 변경 파일 표)이 이미 명시했고, 이 프로젝트 컨벤션과도 일치한다:**

1. **신규 `tests/e2e/swupdate.spec.ts`** — E1~E7 (STUB 환경, 프로덕션 빌드 필요)
   - 근거: 이 기능은 파일 하나로 감당하기엔 시나리오가 7개로 많고(`hardening.spec.ts`
     는 이미 3개 기능 F-54/F-61/F-62 를 담고 있어 더 얹으면 파일이 비대해진다),
     `fileaccess.spec.ts`/`session.spec.ts` 처럼 **기능 단위 1파일** 원칙을 따르는
     것이 기존 관례와 맞는다.
   - `describe` 이름은 `"F-69 서비스 워커 업데이트 알림"` 로 통일 권장.
2. **기존 `tests/e2e/hardening.spec.ts` 의 `"F-61 PWA"` `describe` 블록에 E8 추가**
   (기술 스펙이 "또는 기존 F-61 블록 확장" 이라 명시한 대안 중 이쪽을 권장)
   - 근거: E8("실제 서비스 워커 회귀 — 오프라인과 등록이 그대로다")은 이미 존재하는
     `"배포 환경에서 서비스 워커가 등록된다"` 테스트와 **같은 REMOTE 판정 로직
     (`isRemote(baseURL)`)과 같은 관심사(오프라인 회귀)**를 공유한다. 새 파일을
     만들면 `isRemote()` 를 복제하거나 별도로 export 해야 하는데, 현재
     `isRemote()` 는 `hardening.spec.ts` 파일 스코프 함수라 export 돼 있지 않다.
     같은 블록에 넣는 편이 함수 재사용·리뷰 동선 양쪽에서 더 안전하다.
   - 새 테스트는 기존 테스트 **뒤에 추가**만 하고 기존 4건(F-54 2건 + F-61 3건 +
     이미 있는 등록 테스트)의 순서·내용은 건드리지 않는다.

## STUB 실행 환경 — playwright.config.ts 에 필요한 것 (참고용, 구현은 STEP 5)

기술 스펙 §12.2: STUB 시나리오(E1~E7)는 `import.meta.env.PROD` 가드 때문에
**프로덕션 번들**(빌드 + `vite preview`)에서만 `register()` 가 호출된다. 즉 현재의
단일 `webServer`(vite dev 서버) 설정만으로는 E1~E7 을 실행할 수 없다.

`playwright.config.ts` 에 필요한 조정 방향(기술 스펙이 이미 결정, STEP 5 dev-frontend
구현 대상 — 본 에이전트는 코드를 만들지 않는다):
- 환경변수(예: `E2E_PREVIEW=1`)로 선택 시 `npm run build && npm run preview` 를
  `webServer.command` 로 쓰는 별도 프로젝트/설정을 추가.
- 기본(dev 서버) 실행에서는 `swupdate.spec.ts` 의 STUB 케이스를 skip 하고, 스킵 사유는
  `"프로덕션 번들에서만 서비스 워커가 등록된다"` 로 통일(기술 스펙 §12.2 문구 그대로).
- `package.json` 에 새 스크립트가 필요하면 기존 `test:e2e`/`test:e2e:report` 명명
  규칙(`test:e2e:<수식어>`)을 따른다 (예: `test:e2e:preview`).

## U10 STUB 설계 스케치 — fixtures 구현 (본 에이전트가 추가함)

`tests/e2e/fixtures.ts` 에 다음을 **추가만** 했다(기존 export 4개는 시그니처·동작
무변경):

- `installSwUpdateStub(page, { controlled, waitingOnLoad })` — 앱 스크립트 실행 전에
  `Navigator.prototype.serviceWorker` 를 가짜 객체로 치환한다. 기술 스펙 §4.2
  `SwUpdateHost` 가 기대하는 표면(`register()`/`registration.waiting`/
  `waiting.postMessage`/`controllerchange`)만 흉내 낸다.
  - `controlled: false` → `navigator.serviceWorker.controller === null` (최초 설치,
    E1 용)
  - `controlled: true` → 활성 워커가 이미 페이지를 제어 중 (E2~E7 용)
  - `waitingOnLoad: true` → `register()` 직후부터 `registration.waiting` 이 채워져
    있음 (경로 A)
- `triggerSwUpdateFound(page)` — 경로 B(세션 중 새 워커 설치)를 시뮬레이션.
  `updatefound` → `installing` → `statechange`("installed") 순으로 발화한다.
- `triggerSwControllerChange(page)` — 사용자가 갱신을 수락한 뒤 도착하는 활성화 완료
  신호(`controllerchange`)를 발화한다. **E7(무응답 타임아웃 케이스)에서는 이 함수를
  호출하지 않으면 된다** — 스텁은 자동으로 신호를 보내지 않으므로 앱의 3000ms
  타임아웃 경로가 자연스럽게 트리거된다.
- `getSwWaitingPostMessageCalls(page)` — 대기 워커(또는 활성화 후 컨트롤러)에 전달된
  `postMessage` 호출 횟수/내용을 조회한다. E7 의 "연타해도 1회만 전송" 단언에 쓴다.

이 스텁은 `window.__swStub` 전역에 제어 핸들을 얹는 방식으로, 기존 `__fsMock` 패턴과
동일한 관례를 따른다. 타입 선언은 `types.d.ts` 에 `E2ESwStub` 인터페이스로 추가했다
(기존 `E2EFsMock` 선언 옆, 무변경 추가).

**STEP 5 구현자(dev-frontend) 확인 필요 사항**: 이 스텁은 기술 스펙을 근거로 설계했지만
실제 `swUpdate.ts` 구현과 표면이 100% 일치한다는 보장은 없다(예: `registration.update()`
호출 스파이가 필요하면 스텁에 카운터 추가 필요, FR-S1/S2 능동 확인 검증 시). `swupdate.spec.ts`
작성 중 표면이 안 맞으면 `installSwUpdateStub` 를 **확장**(기존 옵션/반환값은 유지하며
추가)하는 방향으로 조정할 것 — 기존 4개 export 는 다른 스펙 파일이 의존하므로 시그니처를
바꾸지 않는다.

## 마이그레이션 권고

현 구조(flat spec + 단일 `fixtures.ts`)는 스펙 파일이 10개를 넘어가면 탐색이 불편해질
수 있다. 그 시점에 `pages/`(있다면 POM 후보 없음 — 이 앱은 폼 기반 페이지가 아니라
단일 SPA 화면이라 POM 이점이 크지 않음)보다는 **`fixtures.ts` 를 `fixtures/` 디렉토리로
나누는 것**(예: `fixtures/fsMock.ts`, `fixtures/swStub.ts`)을 권한다. 지금은 파일 10개
미만이라 이관 불필요.

## package.json / config.json 관련

- `package.json` 은 이미 `@playwright/test` devDependency 와 `test:e2e`/`test:e2e:report`
  스크립트를 갖추고 있어 병합 대상이 없다. `config.json` 의 `e2e_*` 필드(로컬/원격
  baseURL)는 이 저장소가 아직 쓰지 않으며, `playwright.config.ts` 는 `E2E_BASE_URL`
  환경변수로 원격 baseURL 을 직접 받는 방식(`isRemote()` 판정과 함께)을 쓴다 —
  `${cf_dev_url}` 변수 참조 문법은 이 저장소에는 아직 적용돼 있지 않다.

# 이슈 #31 (F-25 스크롤 동기화 + F-72 편집/프리뷰 시각 구분)

본 이슈도 이슈 #8 과 같은 이유로 **템플릿 골격 복사를 하지 않았다**(Q5 보호,
위 절 그대로). 여기서는 이 이슈에 한정된 배치 판단·판정 기준·주의점만 적는다.
기술 스펙(`## ⚙️ 기술 스펙` §10 "E2E 검증 시나리오")이 이미 시나리오 6건(E1~E6)과
공통 테스트 데이터(DOC-A~D)를 확정했으므로, 여기서는 **그 결정을 이 저장소
컨벤션에 맞춰 파일로 어떻게 쪼갤지**만 판단한다.

## 어디에 둘 것인가 — 신규 `tests/e2e/scrollsync.spec.ts`

**판단: 신규 파일을 만든다. 기존 파일에 얹지 않는다.**

- **네이밍**: `scrollsync.spec.ts` — 기존 컨벤션(`hardening`·`fileaccess`·`toolbar`
  처럼 소문자 단일 단어, camelCase 금지)을 그대로 따른다. 기술 스펙 §8.1 변경 파일
  표도 `tests/e2e/scrollsync.spec.ts` 로 명시했다 — 스펙과 컨벤션이 이미 일치한다.
  소스 모듈 이름은 `scrollSync.ts`(camelCase)이지만 **테스트 파일명은 소스 파일명을
  따르지 않는다** — 이 저장소의 기존 파일들도 소스와 1:1 이름 매칭이 아니다
  (`toolbar.spec.ts` ↔ `toolbar.ts` 는 우연히 같지만 `hardening.spec.ts` 는 세 모듈
  F-54/F-61/F-62 를 함께 담는다).
- **왜 기존 파일에 얹지 않는가**: 후보로 `editor.spec.ts`(디바운스 렌더 관련)와
  `tabs.spec.ts`(탭 전환 관련)를 검토했다. 두 파일 모두 이번 이슈의 시나리오 일부와
  "관심사가 겹치는 것처럼" 보이지만(E5 는 디바운스, E4 는 탭 전환), 실제로는
  **다른 것을 검증**한다 — `editor.spec.ts`/`tabs.spec.ts` 는 각 모듈의 **고유
  책임**(디바운스 타이밍 자체, 탭별 콘텐츠·커서 격리 자체)을 검증하고, 이번
  시나리오는 그 위에 얹힌 **횡단 관심사**(두 패널의 스크롤 위치가 서로 맞는가)를
  검증한다. `hardening.spec.ts` 에 F-69 E8 을 얹은 선례는 "같은 판정 로직
  (`isRemote`)·같은 관심사" 였기 때문이지, 여기는 그 조건이 성립하지 않는다.
  섞으면 두 파일의 실패 원인이 뒤섞여 리뷰·디버깅 동선이 나빠진다.
- **파일 내부 구조**: `describe` 를 두 개로 나눈다.
  - `"F-72 편집/프리뷰 시각 구분"` — E1 (배경색·경계선 계산 스타일 단언)
  - `"F-25 스크롤 동기화"` — E2~E6 (동기화 본체)
  기능 ID 가 둘이라도 **파일은 하나**다. PRD 가 두 요구를 "하나의 목표"로 명시적으로
  묶었고(§1), M1~M3(시각 구분)이 M4~M13(동기화)보다 먼저 성립해야 동기화 검증 시
  "어디가 경계인지"를 사람이 눈으로 확인할 수 있다는 마일스톤 순서 의존(PRD §8)도
  한 파일 안에서 위→아래 순서로 자연스럽게 반영된다.

## 판정 기준 — 실행 가능한 형태로 (기술 스펙 §10.1/§10.2 근거)

| 시나리오 | 판정 | 오차/허용 범위 |
|----------|------|----------------|
| E1 시각 구분 | `#editor`/`#preview` 계산된 배경색이 서로 다르고, `--surface-editor`/`--surface-preview`/`--border-split` 세 커스텀 속성이 스타일시트에 선언돼 있다 | 정확 일치(색상값은 리터럴 비교) |
| E2 끝점 정합 (에디터→프리뷰) | 맨 아래: `preview.scrollTop`≈`scrollHeight-clientHeight`. 맨 위: `preview.scrollTop === 0` | 맨 아래 **≤ 2px**, 맨 위 **정확히 0**(오차 없음) |
| E3 양방향·루프 없음 | 마지막 조작 쪽이 소스, 1초 대기 후 두 패널 모두 정지 | 대기 시작·종료 시점 값이 **완전히 같다**(0px) |
| E4 탭 복원 | 에디터 `scrollTop` 이 이탈 시점 값과 같다 | **≤ 5px**(F-06 무회귀, 정확한 0 이 아니라 근사) |
| E5 재렌더 후 유지 | 프리뷰 스크롤이 재렌더 전 값과 같다 | **프리뷰 창 높이의 10% 이내** |
| E6 코드 블록 혼재 (중간부) | 앵커가 보이거나, 뷰포트 경계로부터 **프리뷰 창 높이 1개 이내** | 근접이면 통과 — **완전 일치 요구 금지** |

> **경고 — "완전 일치" 단언을 쓰지 말 것.** E6(그리고 균질 산문의 중간부 전반)은
> 기술 스펙 §10.2 가 "완전히 같은 줄"을 요구하지 않는다고 명시했다. 이것은
> **누락된 정밀도가 아니라 PRD §3(b)가 의도적으로 선택한 설계**다(비율 기반 매핑 —
> 라인 매핑은 F-18 보안 불변식을 건드려 기각). `expect(anchorTop).toBeCloseTo(...)`
> 류의 좁은 허용치를 중간부에 걸면, **의도된 근사를 버그로 오판하는 가짜 실패**가
> 나온다. 정밀 일치를 요구해도 되는 곳은 **양 끝(scrollTop=0 / scrollHeight-clientHeight)
> 뿐**이다 — 그 외 전부는 "화면 안에 있다/근접해 있다"로만 판정한다.

## 스크롤 E2E 작성 시 주의점

1. **`scroll` 이벤트는 버블링하지 않는다.** `page.on(...)` 이나 `document` 레벨
   감시로는 `#editor`/`#preview` 의 스크롤을 잡을 수 없다 — 반드시 해당 요소의
   `scrollTop`/`scrollHeight`/`clientHeight` 를 `page.locator(selector).evaluate()`
   로 직접 읽는다(`getScrollMetrics()` 헬퍼가 이미 이렇게 되어 있다). 이건 앱
   구현(`scrollSync.ts`)이 리스너를 각 패널에 직접 붙이는 이유이기도 하다 — 프리뷰
   내부 `pre`/`table` 의 가로 스크롤(E9)이 세로 동기화를 오발화하지 않게 하려는
   설계이므로, 테스트도 같은 경계를 존중해야 한다.
2. **프로그램적 스크롤과 사용자 스크롤은 이벤트만으로 구분되지 않는다.** 앱은
   `expectedTop` 값 비교(R2)로 이를 구분하지만, 이는 **테스트가 유발한 스크롤에도
   똑같이 적용된다** — `el.scrollTop = x` 로 직접 대입해도 실제 `scroll` 이벤트가
   발화하므로 앱 입장에서는 진짜 사용자 스크롤과 구분되지 않는다. 즉 이 방식은
   판별 로직을 우회하는 편법이 아니라 **유효한 자극**이다.
3. **`mouse.wheel(dx, dy)` vs `evaluate(el => el.scrollTop = x)` 는 다른 도구다.**
   - `evaluate` 대입 — 목표 좌표에 **정확히 한 번에** 도달. 끝점 정합(E2 양 끝)처럼
     **정확한 좌표**가 필요한 단언에 쓴다.
   - `mouse.wheel` — 실제 휠 이벤트를 여러 번에 걸쳐 보내 브라우저가 자체
     가감속으로 처리한다. 목표 좌표를 보장하지 않지만 "연속 스크롤 이벤트가 여러 번
     온다"(AC-14 프레임 병합, E3 의 진동 여부) 같은 **연속성 자체**를 검증할 때 쓴다.
   - 한 단언 안에서 두 방식을 섞지 말 것 — 오차 허용치가 다르다(위 표 참고).
4. **탭 전환(E4) 검증에는 파일 목이 필요 없다.** 기술 스펙 §10.4 가 이미
   "New 버튼/Alt+N 으로 탭을 만들어 파일 목 의존을 없앤다" 고 결정했다 —
   `installFsMock()` 을 쓰지 않는다.
5. **`beforeEach` 컨텍스트 격리에 의존한다.** 별도 `afterEach` 정리는 불필요하지만,
   E4 는 탭을 2개 만들므로 같은 브라우저 컨텍스트를 재사용하는 실행 방식(예: 수동
   `--repeat-each` 튜닝)에서는 세션 복원(F-20)이 이전 탭을 되살릴 수 있다는 점을
   기술 스펙 §10.5 가 명시했다 — 기본 `test.describe` 격리를 그대로 유지한다.
